# Бинарный поиск: шпаргалка по тонкостям

## Два разных шаблона — не смешивать

### 1. Классический поиск значения (exact match)

Ищем конкретный `target`, ответа может не быть.

```go
i, j := 0, len(nums)-1
for i <= j {                    // НЕстрогое: последний элемент тоже проверяем
    mid := i + (j-i)/2
    if nums[mid] == target {
        return mid
    } else if target < nums[mid] {
        j = mid - 1             // mid проверен → исключаем
    } else {
        i = mid + 1
    }
}
return -1                       // "не нашли" — легальный исход
```

Признаки: есть `== target`, обе ветки исключают `mid`, возможен `-1`.

### 2. Поиск границы по инварианту (lower/upper bound)

Ищем первый индекс, где предикат становится истинным. Ответ существует всегда (или обрабатывается отдельно).

```go
i, j := 0, len(nums)-1
for i < j {                     // СТРОГОЕ: иначе бесконечный цикл
    mid := i + (j-i)/2
    if predicate(mid) {
        j = mid                 // mid может быть ответом → НЕ исключаем
    } else {
        i = mid + 1
    }
}
return i                        // i == j — это и есть ответ
```

Признаки: нет `== target`, одна из веток `j = mid` (без `-1`), возвращаем `i` после цикла.

Этим шаблоном решаются: минимум в rotated array, peak element, first bad version, nextGreatestLetter, любой lower/upper bound.

## Правило выбора условия цикла

| Ветки сужения                  | Условие цикла | Почему |
|--------------------------------|---------------|--------|
| `j = mid - 1` и `i = mid + 1`  | `i <= j`      | окно строго сужается всегда; при `i < j` теряется последний элемент |
| `j = mid` и `i = mid + 1`      | `i < j`       | при `i == j == mid` ветка `j = mid` не сужает окно → бесконечный цикл (TLE) |

Мнемоника: **если `mid` остаётся в окне — цикл строгий**.

## Типовые ошибки (все были в этом чате)

1. **Опечатка в индексе**: `nums[mid]-1 > nums[mid]` вместо `nums[mid-1] > nums[mid]`.
   Первое — «значение минус один», всегда ложь. Компилятор не спасёт.

2. **`for i < j` в exact-поиске**: последний оставшийся элемент не проверяется.
   `[5]`, target 5 → вернётся `-1`.

3. **`for i <= j` в boundary-поиске с `j = mid`**: бесконечный цикл.

4. **Ранние выходы, ломающие инвариант**: `if mid == 0 || mid == len-1 { return mid }`
   возвращает край *окна поиска*, а не искомую границу. В boundary-шаблоне
   ранние выходы не нужны вообще — цикл сам сходится к ответу.

5. **Забытый wrap-around / «ответа нет»**: если все элементы `<= target`,
   поиск честно сойдётся к последнему элементу, но он не удовлетворяет условию.
   Либо проверка после цикла, либо (лучше) — см. полуинтервал ниже.

## Полуинтервал `[i, len)` — идиоматичная форма bound-поиска

```go
i, j := 0, len(nums)             // j ЗА последним элементом
for i < j {
    mid := i + (j-i)/2
    if nums[mid] <= target {
        i = mid + 1
    } else {
        j = mid
    }
}
// i == len(nums)  ⇔  подходящего элемента нет — легальное значение, не особый случай
```

Так устроен `sort.Search` в stdlib. Для циклического ответа (nextGreatestLetter):
`return letters[i % len(letters)]`.

## Мелочи

- **`mid := i + (j-i)/2`**, а не `(i+j)/2` — защита от переполнения. На практике
  на int64 не выстрелит, но это дешёвая привычка и стандарт на собеседованиях.
- **Убирать `fmt.Printf` перед сабмитом** — на LeetCode отладочный вывод
  ощутимо замедляет решение и портит время.
- **Как проверить решение головой**: прогнать на окнах размера 1 и 2.
  Размер 2 — главный источник бесконечных циклов (проверьте, что `mid`
  и ветки реально сужают окно). Размер 1 — проверка условия выхода.

## Как распознать boundary-задачу

Переформулируйте: «найти первый индекс, где P(i) истинно», причём P монотонен
(false…false, true…true). Тогда:

- минимум в rotated array: `P(i) = nums[i] <= nums[len-1]`
- peak element: `P(i) = nums[i] > nums[i+1]`
- nextGreatestLetter: `P(i) = letters[i] > target`
- first bad version: `P(i) = isBad(i)`

Если предикат сформулировался — пишете шаблон №2 не думая.
